# 技术栈调研：maplibre 自绘 vs OpenLayers + ol-plot

> 结论先行：**本项目选择 maplibre-gl + 自研标绘几何库**。理由是——我们需要的是「史料态势的静态回放」，而 ol-plot 的价值集中在「让用户在地图上交互式点选绘制标绘」。二者不匹配。详见下文，包括在什么条件下这个结论会翻转。

## 1. 先把需求拆成约束

态势图能力不是笼统的一句「要能画箭头」。真正决定技术选型的是下面四个问题：

| 问题 | 本项目的答案 | 对选型的含义 |
| --- | --- | --- |
| 标绘图形是**预定义**的，还是**用户现场绘制**的？ | 预定义。四渡赤水四个阶段的箭头、集结地、防线坐标全部硬编码在 `src/data/situations/*.ts` 里 | 不需要交互式绘制工具，只需要几何生成 + 渲染 |
| 标绘需要**编辑、拖拽控制点、持久化**吗？ | 不需要 | ol-plot 的核心能力（Plot 控件、控制点编辑）全部用不上 |
| 标绘需要**随缩放自适应**吗？ | 需要。箭头宽度以「千米」定义，缩放时按地理尺寸缩放，保证在任意层级量得准 | 只要几何在投影平面内生成，任何引擎都能做到 |
| 底图、路线动画、节点标签的体量与性能要求？ | 需要一张可离线的中国地形底图 + 30 段路线 + 50 个 DOM 标注 | 底图自由度和包体积比标绘库更重要 |

一句话概括：**这是一个「读」的态势图，不是一个「画」的态势图。**

## 2. ol-plot 是什么，它解决什么问题

`ol-plot`（sakitam-fdd/ol-plot）是 OpenLayers 生态里最成熟的军事标绘库，当前版本 `4.2.0`（2026-07 仍在维护），`peerDependencies: { ol: ">=6.15.0 <11" }`。

它的能力模型是：

```
Plot 控件（绑定 ol.Map）
  └── plot(type, params)  →  进入绘制模式，鼠标点几下
        └── 生成 ol.Feature + ol.style.Style 挂到 VectorLayer
              └── 支持控制点编辑、样式修改、序列化
```

典型标绘类型包括：

- 箭头族：直箭头、细直箭头、突击方向、进攻箭头、钳击箭头、燕尾箭头
- 面状族：矩形、圆形、椭圆、多边形、自由线、弓形、曲线
- 阵地族：集结地、防御阵地、阻击阵地

**它的强项**是几何算法的积累 + 与 OL 渲染体系的深度绑定。如果你要做的是一个「参谋在图上标绘作战方案」的工具，ol-plot 能省下大量工作。

**它的代价**：

1. **强绑定 OpenLayers**。标绘几何全部包裹在 `ol.Feature` / `ol.geom` / `ol.style.Style` 里，无法移植到 maplibre 的 GeoJSON source + style layer 体系。
2. **要为不需要的能力付费**。引入 ol-plot 就要引入 OpenLayers（约 600KB 未压缩），即便我们一个控件都不会用。
3. **样式系统割裂**。态势图之外，路线动画、节点动效、DOM 标注这些部分用 maplibre 或原生 DOM 更顺手；两套渲染体系并存会让代码分裂成两个心智模型。

## 3. maplibre 自绘可行吗？实测结论：完全可行

箭头的本质是一段**多边形几何计算**，与地图引擎无关：

```
输入：路径点列 + 箭身宽 + 翼展 + 箭头长度 + 尾部收窄比例
输出：一个闭合多边形环（经纬度）
```

本项目在 `src/plot/` 里实现了这套算法，共约 340 行 TypeScript，零第三方依赖：

| 文件 | 职责 | 行数 |
| --- | --- | --- |
| `src/plot/geo.ts` | Web Mercator 投影、折线重采样、切线/法向、Chaikin 平滑、贝塞尔 | ~140 |
| `src/plot/plot.ts` | 进攻箭头、钳击双箭头、集结地、防御阵地、阻击点 | ~210 |

核心算法的处理链条：

```
经纬度路径
  → 投影到 Mercator 米制平面（保证「宽度 8 公里」量得准）
  → Chaikin 平滑（让手绘般的折线自然）
  → 按弧长重采样
  → 每个采样点算法向量，按 tailTaper→1 的宽度梯度生成左右两条边
  → 在箭身末端外扩到 headWidth/2 形成双翼
  → 接上路径终点作为箭尖
  → 反投影回经纬度，输出闭合环
  → maplibre fill layer + line layer 渲染
```

实测效果（四渡赤水态势图）：进攻箭头、钳击箭头、集结地椭圆、防御阵地锯齿线全部正常渲染，可随地图缩放保持地理尺寸，且能与路线图层、DOM 标签共存于同一张地图。

**渲染分工**：

| 元素 | 渲染方式 | 原因 |
| --- | --- | --- |
| 标绘面（箭头/集结地/防线） | maplibre `fill` + `line` layer | 矢量、可随缩放重绘、性能好 |
| 部队番号文字 | DOM Marker | 中文字体无需 glyph 服务，且可做 CSS 动效 |
| 行军路线 | maplibre `line` layer + GeoJSON | 支持 dash 流动动画、按部队过滤 |
| 节点标注 | DOM Marker | 同上，且需要悬停/选中态 |

## 4. 逐项对比

| 维度 | maplibre 自绘 | OpenLayers + ol-plot |
| --- | --- | --- |
| 预定义标绘渲染 | ✅ 完全满足（本项目已验证） | ✅ 满足 |
| 用户交互式绘制 | ❌ 需自己实现（本项目不需要） | ✅ 开箱即用 |
| 控制点编辑 | ❌ 需自己实现 | ✅ 开箱即用 |
| 标绘几何算法积累 | ⚠️ 需自己写（本项目约 200 行核心算法） | ✅ 20+ 种图形现成 |
| 与中式主题底图配合 | ✅ 自由度高 | ⚠️ 受 OL 样式体系约束 |
| 额外依赖体积 | 0（已用 maplibre） | +约 600KB（OpenLayers） |
| 包体积（gzip 后整个应用） | 主包 36KB + maplibre 299KB | 若两者都要则翻倍 |
| 两套渲染体系并存风险 | 无 | 有（OL 画标绘、其他可能用别的） |
| 学习/维护成本 | 需要理解几何算法 | 需要理解 ol-plot 的控件生命周期 |

## 5. 结论与适用边界

### 结论

**选 maplibre-gl + 自研标绘几何库。** 三条理由：

1. **能力匹配**：本项目态势图是「史料回放」，图形参数预定义，不需要 ol-plot 的交互绘制；
2. **成本更低**：自研算法约 200 行，比引入 OpenLayers 并适配两套渲染体系更轻；
3. **架构统一**：底图、路线、节点、标绘共用 maplibre 的 GeoJSON source 与样式系统，只有一套心智模型。

### 什么情况下这个结论会翻转

如果项目后续要加这些功能，就应当重新评估 ol-plot（或等价的专用标绘库）：

- **让用户在图上自己画态势**（教学演练、兵棋推演）；
- 需要**控制点拖拽编辑**并保存标绘结果；
- 需要 **20+ 种标准军标**（含队标、兵器标、气象标）；
- 需求从「一幅叙事地图」变成「一个标绘编辑器」。

真到那一步，务实的做法不是硬改 maplibre，而是**双引擎**：maplibre 负责底图与叙事层，OL + ol-plot 作为一个只负责标绘的叠层接进来——但这会付出两套相机同步、坐标系对齐的代价，属于另一个量级的工程。

### 本项目保留的扩展点

`src/plot/plot.ts` 的图形生成函数是纯函数（输入经纬度，输出经纬度数组），与 maplibre 无耦合。若将来要接 ol-plot 或换引擎，这层几何代码可以原样保留；反过来，若要自研更多军标，只需要往这个文件里加函数，再在 `src/map/situation.ts` 的 switch 里挂一条分支。

## 6. 底图方案的独立取舍

技术栈里还有一项重要决策：**底图从哪来**。

本项目最终选择了「预烘地形 + 本地矢量」，而不是在线瓦片服务：

| 方案 | 问题 |
| --- | --- |
| 高德/天地图瓦片 | 需要 API key，有商用授权限制，离线不可用 |
| OpenStreetMap / Carto | 国内访问不稳定（实测 Carto、OpenFreeMap 均连接失败），且中文标注薄弱 |
| MapTiler / 商业矢量 | 需要 key，有配额 |
| **预烘地形（本项目）** | Terrarium DEM（SRTM/GMTED）一次性烘成 3072×2816 的山体阴影 PNG，7.9MB，配合本地省界 GeoJSON 与河流，**完全离线、零 key、零请求** |

代价是放大到 10 级以上时地形会糊——但对于「看长征全貌」这个用途，6~8 级是主要阅读区间，够用。若将来需要更深缩放，把烘焙脚本的 `Z` 从 7 提到 8 或 9 即可，代价是图片体积翻倍。
